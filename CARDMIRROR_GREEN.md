# CardMirror Green

Personal fork: https://github.com/paulicydebate/CardMirror-Green
Active branch: `feature/full-card-api`. PR #1 remains draft; do not merge or modify main.

## Two computers

Install the Windows x64 preview on the desktop and the macOS ARM64 preview on an Apple Silicon Mac. Both artifacts come from the same desktop-previews workflow run and commit. Preview artifacts currently expire after 90 days. Install the Green build alongside upstream CardMirror; Green uses a distinct installer ID, executable, settings folder and bridge identity. Windows releases use the Green-only in-app updater from v1.16.1 and Mac ARM64 from v1.16.4; older previews need one manual install.

If an earlier preview replaced upstream CardMirror, installing Green does not restore upstream automatically. Reinstall upstream separately if desired. Green starts with its own empty profile; existing files on disk can be opened normally. Do not copy a running app profile between machines.

Source code is shared through GitHub. For a local development checkout on either machine:

```sh
git clone --branch feature/full-card-api https://github.com/paulicydebate/CardMirror-Green.git
cd cardmirror
npm ci
npm --prefix apps/desktop ci
```

Before switching machines, commit and push changes on the feature branch. On the other machine use `git pull --ff-only` in a clean checkout. Install dependencies separately on each operating system; do not sync node_modules or installer output through cloud storage.

Documents can live in a shared Dropbox/OneDrive folder installed on both computers. Save and close a document, wait for sync, then open it on the other computer. For simultaneous editing use CardMirror's collaboration feature rather than editing two cloud-file copies at once. Settings, Quick Cards and local recovery/history stores are per machine; this change does not add automatic profile synchronization.

To continue the same assistant chat and desktop workspace from another device, use the app's Settings > Connections remote-control setup where available, under the same account/workspace. The desktop must stay awake, online and running the app. This is remote access to the desktop, not a copy of its files. See https://learn.chatgpt.com/docs/remote-connections .

## Current API milestone

`CardMirrorPluginApi.structuredCards()` reads the active document's full cards and analytics without changing the document or assigning a document ID. It preserves citation/body paragraphs, inline text runs and marks, stable card IDs when available, and document offsets. Derived self-reference and transclusion subtrees are skipped.

The extraction tests now live in `tests/editor/structured-card-extract.test.ts`, where the configured Vitest runner discovers them. Coverage includes multiple citations/paragraphs, missing IDs, offsets, derived-copy exclusion, mark attributes, native save/reopen, and plugin API integration.

Representative document validation and the version 1 local batch-export contract are implemented. See CARD_INGEST_V1.md for the format and ROADMAP.md for completed and planned work. Next is the OpenCaselist ingestion adapter; no remote downloader or ingestion service is shipped yet.

The collaboration backoff-cap regression uses fake timers and a pinned high jitter draw, so its 50 ms cap is checked without relying on runner scheduling latency.

Home → **New flow** (or command bar → New Flow). Sheets per position, one column per speech (NPDA first, also NFA-LD and policy), cells that wrap, keyboard-first. ## Prep document guards (Codex, 2026-10-26)

The next layer is implemented in `src/editor/prep-document-guard.ts` and included in the shared editor plugin stack. **It stays inert until the future session controller supplies a policy; there are still no Prep / Round controls or active protections in the shipped app.**

- Per-editor capture listeners block copy/cut/paste/drag/drop and clipboard-related `beforeinput` events before ProseMirror or flow handlers can consume them. Each listener checks its own root and owning session uid, so unrelated panes and UI fields remain unrestricted. Destroying a view removes its listeners.
- The transaction guard caps additions at 40 characters across all steps and flow cells, including same-size text replacements and the flow Prep column. It refuses even short paste/drop/cut transactions carrying the native UI-event tag. Pure formatting stays allowed. Flow fields are compared by sheet/row identity; unchanged flow attributes are skipped and parsed fields are cached by immutable node identity.
- Keyboard macros and the shared autocorrect engine tag conversions/reverts for an explicit allowed-and-audited path. Undo/redo restores are allowed and large restores flagged. Already-merged remote edits must be admitted to avoid CRDT divergence; their large inserts are flagged. The future controller still needs to gate prep collaboration membership, attach partner names, and disconnect collaboration on log failures.
- Accepted changes are audited during plugin state application, not speculatively from the filter. A later plugin rejecting a transaction therefore does not produce a false accepted-change event. These events describe committed text changes, not a complete raw-keystroke log; raw input/composition, focus and lifecycle recording still need the controller.
- Fixed the flow NodeView's optimistic edit path: rejected edits now restore the visible textarea and local workbook from the authoritative editor state. Rejected content cannot leak into a later allowed edit, and rejected edits do not enter the local co-edit merge history. Covered in grid and column-as-document views.
- Validation: 27 new guard tests, plus existing macro/autocorrect/flow/real-Loro co-edit suites: **77 tests pass** on local Windows/Node 24.21.0. Root typecheck and production renderer/PWA build pass (existing chunk-size/dynamic-import warnings remain).
- Next: IPC/controller and mode commands; verify that new/open/recovered/switch-mode/pop-out paths always bind the guard to the correct stable document uid before enabling it (some single-doc paths currently assign their new uid after mounting). Add main-process clipboard and external-route refusals, Round file-open gates and save/close coordination, prep-aware collaboration, log batching/viewer/export, and packaged-app two-window/three-pane checks. The renderer policy setter is an internal integration API, not a UI toggle. This layer alone is not a tournament-ready protection mode.

## Usable Prep / Round Modes (Codex, 2026-10-26)

The controller, native gates and UI are now connected. The two preceding foundation/guard sections describe earlier, inactive milestones; **this section is the current status**. Work stays on `feature/full-card-api`, with PR #1 draft and main unchanged.

Use the desktop's **Prep / Round** bar (or the File command group):

1. **Start Prep** confirms local logging. Existing strategy documents stay unrestricted.
2. **New prep doc** or **New prep flow** creates and immediately protects an empty document. The flow button uses NPDA; normal New Flow still offers all presets and creates a protected blank flow during a session. **Mark as prep** only accepts a still-blank document created during this Prep session, with no live co-editing session. Text entered before a mark cannot be retroactively attested.
3. Protected editors/panes have yellow outlines. Clipboard APIs, copy/cut/paste, drag/drop, external insertion, send-to-speech, Quick Card insertion, live references and large transaction/flow additions are blocked at their relevant boundaries. Macro/autocorrect expansions remain allowed and logged. Undo/redo and merged remote changes are logged; large restores/remote additions are flagged.
4. **Start Round** asks for confirmation, waits for every ready editor window to stop collaboration and close all non-prep documents, and shows normal save prompts. Canceling any prompt keeps Prep Mode (documents already closed remain closed). The native owner checks the final inventories before committing Round. A document hidden behind Home still counts as open and must close.
5. Round draws a red border in all editor windows, blocks existing-file dialogs/recents/OS-open/read/history/browse/OpenCaselist routes, and stops the file-index service. Native reads begun before the transition are rechecked before returning content. Saving work remains allowed. New blank windows/documents are allowed and inherit protection. Workspace-layout switching waits until the session ends.
6. **End session** confirms, disconnects protected collaboration, flushes all windows' queued events and seals the log. It displays Prep/ Round/end times, a 16-hex-digit seal code and the complete final SHA-256. **Logs** lists sessions, verifies chains, shows timing, typed characters, per-minute speed estimates, focus intervals, flagged and blocked events, and a filterable event list. Export uses a native Save dialog; logs contain prep text and remain local until explicitly exported.

The durable session resumes after restart. Protected recovery journals reopen automatically, including during Round; unrelated journals do not reach the Round renderer. Prep markings persist across normal Save, Save As and reopening native/Word files with the stored document identity. Pane session uids now use UUIDs, avoiding old counter collisions after a restart. A write/recovery error pauses editing rather than claiming a complete audit trail. Input events are normally sent in 500 ms batches, so an abrupt process/OS failure can lose the last unflushed batch; an ordinary close and End flush first. The log records client input timestamps as well as main-process append times.

Prep collaboration uses a Green-only `cmshare3` / `cmview2` format and a prep flag inside the encrypted seed. Current Green join/resume paths require Prep Mode and protect the received copy before binding. Older builds reject the new code format. A narrow native clipboard route can copy these structured session codes without enabling prep-text copying; prep invitations should be shared with another Green desktop install. The log records available partner names for remote changes; this is not cryptographic attribution of a particular author. Ordinary, non-prep collaboration keeps its existing formats.

**Round Mode setting.** Settings → General → Prep / Round → "Round Mode: Co-Flowing" (`prepRoundCoflow`, off by default).
- **Off (Isolation, the default and the earlier behavior):** Round ends all co-editing. A partner's copy of a shared prep doc closes on their computer without saving: no save prompt, no recovery journal, no session record, no session history, and it drops off recent rooms. While shared, that copy refuses Save, Save As and preset exports. The partner's own prep docs stay open. The host ending the shared doc at any time also closes the partner's copy, including for a partner who was offline and reconnects later.
- **On (Co-Flowing):** Round keeps co-editing shared prep docs and flows. Non-prep sessions still end, and starting or joining new sessions stays blocked; reconnecting to a Co-Flowing prep doc is allowed. End session disconnects as before, and the partner keeps their copy.
- **Where the choice lives:** the host's setting is written into the shared doc (`cardmirrorGreenRoundMode` in the encrypted room meta) when sharing starts. Both computers follow that per doc; docs shared before this change act as Isolation.
- **Logging:** kept sessions are logged as `collaboration-kept`, and closed copies as `collaboration-ended` with `closedCopy`.
- **Limit:** a modified client could ignore the close.

**Check Prep Document.** At End, each window sends a content fingerprint of every open prep doc (`src/editor/prep-fingerprint.ts`). The fingerprint is a SHA-256 of text, structure, formatting values, flow cells and images; it leaves out ids, comment anchors, reading markers and column widths. Main appends a `document-fingerprints` entry just before `session-end`, so the 16-hex-digit seal code covers it.
- **Certificate:** those two entries form a small certificate. It is broadcast to every window and saved inside each sealed prep doc's .cmir file (`prepSeal`, keyed by the file's docId), and it survives reopen and save.
- **The command:** "Check Prep Document" (command bar, File group, status-bar menu when no session is running). It asks for the seal code and reports one of: unchanged, changed after the round, code doesn't match, seal damaged, or not in this seal. It also shows the prep, round and end times.
- **Why the code can't be faked:** forging a matching seal means finding a 64-bit hash match, which is why the code stays 16 characters.
- **Limits:**
  - Word (.docx) saves don't carry the seal.
  - Prep docs closed before End are not fingerprinted.
  - The debater must save the .cmir after End, and the end dialog says so.

**Tests:**
